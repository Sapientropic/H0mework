# CI 与增量构建

[`ci.yml`](../.github/workflows/ci.yml) 处理 `main` 推送、PR 更新和手动运行。README、横幅、许可及作者指南的纯展示改动不触发工作流，冻结来源文档仍参与检查。同一分支或 PR 的新推送取消旧运行；Lean job 定时保存已完成的产物，正常停止时保存最终进度。

## 何时构建 Lean

是否构建由内容决定，与本次推送改了哪些文件无关。[`ci_plan.py`](../tools/ci_plan.py) 为每片计算指纹，再合成完整选集指纹。完整选集指纹由以下内容生成：

- 全部分片指纹；
- 工具链与 manifest；
- 规划脚本与两个工作流文件。

模块指纹包含源码、强编译选项和实际资源输入。包与库的 `weakLeanArgs` 遵循 Lake 的构建规则，不进入指纹；调整其中的编译预算或诊断选项可复用已有产物。`moreLeanArgs` 与 `leanOptions` 仍参与失效判断。首发证明的预算及 trust0／werror 配置见 [lakefile.toml](../Lean/lakefile.toml)。

完整选集的每一片都构建成功、覆盖检查通过后，才以该指纹写入一条验收记录。之后同一内容的运行查到记录，就跳过 Lean。被取消、失败或到期的运行不写这条记录，下一次运行会重新检查。

冻结证据 job 每次运行导出映射校验、低能唯象复核、首发入口检查与工具测试。Bell 与量子载体 job 在主分支推送和手动运行时都会显示；先校验最近一次成功的独立复现 artifact。运行配置、导出映射、复现程序或输入未变时，job 复用该 artifact 并保存复用回执；输入变化，或手动运行将 `full_replay` 设为 true 时，才重新执行。证明编译继续由分片 job 承担。私有期间，Lean 只在手动运行时执行。

Lean 分片在托管 runner 上先加 48 GiB swap，再按 CPU 数设置 `LEAN_NUM_THREADS`，与分工所设的四线程一致。runner 只有 16 GiB 内存，个别生成的判定证明单个模块峰值约 24 GiB；内存耗尽的 runner 会在步骤中途被关闭，日志里只剩 shutdown signal。swap 承接这类峰值；构建结束时日志打印本 job 的内存与 swap 峰值。本地构建仍由 [`build_environment`](../tools/first_release.py) 按每 16 GiB 一槽计算并发；运行日志打印实际并发上限。

## 分工

`make_plan` 从 `lakefile.toml` 的默认库及真实 import 计算模块闭包，沿用各模块的资源依赖、编译参数与库归属。非默认的历史失败库继续通过复现指南中的命令检查。

[`ci_times.tsv`](../tools/ci_times.tsv) 记录每个模块在托管 runner 上的编译秒数，未记录的模块取最近命名空间的中位数。构建按耗时排成若干阶段：同一阶段的各片并行，阶段之间依次进行。

- 依赖链约每 2.75 小时切成一段，每个阶段推进一段。
- 本阶段多片都需要、自身链又很短的模块，先在一个短阶段里单独发布。
- 其余共享依赖由需要它的各片各自构建，完整存档只打包自己负责的模块；进度存档保存范围见[跨运行续建](#跨运行续建)。
- 要等本阶段多片结果才能编译的模块，推迟到下一阶段。
- 每个阶段最多 20 片，对应免费账户的并发上限；阶段数不超过 `ci.yml` 定义的 8 个阶段 job。

分工结果记在 [`ci_layout.tsv`](../tools/ci_layout.tsv)，即每个模块归哪一片。规划时，已登记的模块留在原片。新模块放进它所 import 的分片，或该阶段里还有余量的分片；如果那样要在另一片重编较多依赖，就推迟一个阶段。因此迁入新内容时，已有分片只会增加模块，已存的产物基本都能复用。

每片只下载它实际 import 到的上游存档。全部阶段完成后，完整选集 job 用 Lake 自己列出各默认库的模块，核对每个模块都归属某一片；各片的正确性已由自己的构建保证，所以不必把全部产物解压到同一台机器上。规划结果打印在"构建分工" job 的日志里。

## 迁入新稿件

1. 迁入 Lean 模块后照常提交。CI 会为新模块安排分片，日志会提示有多少模块不在分工表里。
2. 一批迁入告一段落后，运行下面的命令，把新模块的位置写进分工表并提交。此后的迁入不会再挪动它们。

   ```bash
   python3 tools/ci_plan.py plan --update-layout
   ```

3. 新模块第一次构建完成后，用实测耗时刷新耗时表并提交：

   ```bash
   gh run view <run-id> --log > run.log
   python3 tools/ci_plan.py times run.log
   ```

   其他机器的日志用 `--scale` 换算成 runner 秒数。初始表中的本机日志按 2.0 倍换算，倍数来自与 GitHub 实测样本的对照。

4. 日志提示某片预计超过约 3.5 小时，或规划报告阶段数超出时，重新分工并提交。重新分工会让许多模块换片，换片的模块需要重编一次。

   ```bash
   python3 tools/ci_plan.py plan --rebalance
   ```

## 跨运行续建

每片按估计能在单个 job 的期限内完成；估计偏差或 runner 变慢时，每片可以分多次运行完成：

- 每个 job 开始约 5 小时 20 分后停止构建，留出打包和保存的时间。
- 构建期间每五分钟，有新完成模块时将稳定产物保存为进度存档。只收录输出早于完成 trace、复制期间保持稳定的模块；编译中的输出不进入检查点。恢复后仍由 Lake 检查新旧。
- 构建完成时，产物存为该片所属模块的完整存档；失败、到期或被取消时，进度存档还保存本片实际构建的同阶段共享依赖。范围由规划中的 `progress_modules` 指定，打包使用 `pack --checkpoint`，已从更早阶段恢复的产物不重复收录。
- 恢复顺序为完整存档、同一指纹最新的进度、该片最新的任一版本。恢复后由 Lake 的 trace 决定哪些模块仍需编译，存档不会绕过源码与资源检查。
- 完整存档只在整片构建成功后写入，所以已有完整存档的分片直接把它交给下游，不再安装 Lean。
- `main` 上若有分片到期停止，或 runner 关闭使构建步骤被取消，且当前运行确已保存该片的新进度，工作流自动续跑，最多 12 次；续跑排在当前运行之后。同阶段共享依赖完成也计入新进度，下一次可直接复用。编译错误、无新进度或整个工作流被主动取消时不自动续跑。

## 证明存储与缓存

证明产物存放在本仓一个草稿 release（`proof-cache`）的附件里，按平台、工具链、分片名和指纹命名，验收记录也存在这里。草稿不公开显示；附件不会过期，也没有总量上限，单个附件超过约 1.9 GiB 时自动分块。

- 读写草稿需要 `contents: write`，所以规划、Lean 和续跑 job 申请了这项权限。令牌只交给访问存储的步骤，不传给 Lean 编译子进程；检出时不保留凭据。
- 只有 `main` 分支自己的运行写入存储；PR 只读取。
- 完整选集验收通过后，不再属于当前分工的旧存档被删除。当前存档尚未齐全时不删，旧存档继续作为回退。

分片存档保存所属模块的 `.olean`、`.ilean`、生成 C、trace 与哈希文件，排除临时 `.setup.json`，使用 zstd 压缩。job 间传递的短期工件保存一天。`completed_setup_files` 仅清除已有更新编译 trace 的 setup 文件，避免删除仍在使用的编译输入。

Actions 缓存只存放固定依赖（mathlib 等，约 3 GiB）。它在七天未用后被回收，下次从 Mathlib 的缓存服务重新下载，只多花几分钟。

本地查看分工、检查一片已有产物：

```bash
python3 tools/ci_plan.py plan
python3 tools/ci_plan.py build --part s1-01 --check-only
```

在本地访问证明存储时，需设置 `GITHUB_REPOSITORY` 和有该仓写权限的 `GH_TOKEN`。
